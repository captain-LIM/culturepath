# 문화 카테고리별 장소 빈약 문제 개선 계획

> **배경:** 10개 문화 카테고리(`backend/src/config/cultureCategoryMap.js`)로 장소를 찾을 때 개수가 적고 적합도가 낮은 곳이 섞여 있다는 문제가 발견됐다. 원인과 단계별 대응은 아래와 같다.
>
> **최종 갱신:** 2026-08-25

## 원인 요약

1. 장소 제목(title) 정규식만으로 분류해서 재현율이 낮았다.
2. TourAPI 공식 세부 분류 코드(`lclsSystm2`/`lclsSystm3`)를 전혀 안 썼다.
3. FD(음식) 대분류면 키워드 무매칭이어도 `로컬 미식`으로 강제 편입시키는 fallback이 있어 적합도가 낮았다.
4. `/places/search`가 culture별로 직접 검색하지 않고, 지역 기반 일반 검색 결과를 사후 필터링만 한다.
5. 독립서점·책방/전통주·양조장/공예·공방 같은 니치 카테고리는 TourAPI(관광지 중심 공공데이터) 자체에 원천 데이터가 부족하다.

## 3단계 — culture별 능동 검색으로 전환

### 목표

`/places/search?culture=커피·카페`처럼 culture가 지정된 요청은, 지역 기반 일반 목록을 가져와 사후 필터링하는 대신 `searchKeyword2`에 해당 문화의 대표 키워드(예: "카페", "미술관")를 직접 넣어 검색한 결과를 함께 합쳐서 반환한다.

### R16.1 확정 계약

- 카테고리당 안전한 검색어를 최대 3개까지 둔다.
- 첫 페이지의 지역 일반 목록과 첫 검색어를 먼저 조회하고, 엄격한 분류 결과가 요청 개수보다 적을 때만 보조 검색어를 순차 활성화한다. 다음 페이지도 첫 페이지에서 확정한 같은 후보 소스 순서를 사용한다.
- `pageNo`와 `numOfRows`를 지원하며 기본 20개, 페이지당 최대 50개, 통합 후보 재조회 상한은 5페이지다. 이 상한은 단일 요청의 과도한 TourAPI fan-out을 막기 위한 운영 안전장치다.
- 다음 페이지는 앞선 TourAPI 후보 페이지를 누적 재조회하고 페이지별 근거 정렬 후 잘라 내므로, 뒤 페이지의 강한 후보가 앞 페이지 결과를 밀어 중복시키지 않는다.
- 응답 배열은 유지하고 `X-Page-No`, `X-Num-Of-Rows`, `X-Has-More`, 조건부 `X-Next-Page` 헤더를 사용한다.
- 후보 소스 하나가 실패해도 하나 이상 성공하면 검증된 부분 결과를 반환하고, 전부 실패할 때만 공통 외부 API 오류를 반환한다.
- 두 요청 모두 기존 `place_query_cache`를 사용한다.
- 검색어 적중은 후보 발견 신호일 뿐 분류 근거가 아니다.
- 정규화 장소를 다시 분류하고 `contentId override → 공식 중·소분류 → 제목 규칙`으로 정렬한다.
- 실제 TourAPI로 확인한 `AC + 서점/책방`, `EX·VE + 전통주/양조장/소주`만 제목 근거와 함께 허용한다. 행사 대분류 `EV`는 상설 장소로 편입하지 않는다.
- 같은 근거 안에서는 TourAPI 발견 순서를 유지한다.
- 관련도 수치는 공개하지 않고 내부 정렬에만 사용한다.
- 엄격한 필터 뒤 결과가 없어도 가상 ID 장소로 채우지 않는다.

### 예상 변경 파일

- `backend/src/controllers/placesController.js`
- `backend/src/services/tourApiService.js` (필요 시)
- 관련 테스트

## 4단계 — 니치 카테고리 별도 데이터 소스 보완

### 목표

TourAPI에 원천적으로 잘 안 실리는 독립서점·책방 / 전통주·양조장 / 공예·공방 등을 카카오 로컬 API 같은 별도 소스로 보완한다.

### 결정 필요

- 어떤 외부 API를 쓸지 (카카오 로컬 API가 가장 유력 후보)
- 새 소스의 장소 ID를 어떻게 구분할지 (`contentId` 네임스페이스 충돌 방지, 예: `kakao:12345`)
- TourAPI 장소와 중복될 때 병합/제거 기준
- MySQL 스키마·캐시 정책 변경 범위 (임수민 담당 파일과 겹치므로 사전 공유 필요)

### 참고

- 새 외부 API 연동은 기존 PR #4~#9 패턴(공통 클라이언트 → 정규화 → 캐시 → 공개 API 연결)을 그대로 따르는 게 안전하다.
- 5단계 감사 결과로 실제 얼마나 빈약한지 수치를 먼저 보고, 정말 필요한 카테고리에만 착수하는 걸 권장한다.

## 5단계 — culture×지역 커버리지 감사

### 목표

"몇 개 이하면 빈약인지"를 감으로 판단하지 않고, culture×지역 조합별 실제 매칭 개수를 세는 스크립트로 확인한다.

### 2026-08-25 제한 감사 결과

- 대표 14개 지역×문화 조합 중 기존 계약은 7개 조합만 비어 있지 않았다.
- `통영국제음악당`은 정확한 제목 검색에서 정상 `음악` 분류됐지만 대표 검색어 `공연장`으로 발견되지 않았다.
- 전라감영양조장과 안동소주 관련 장소는 검색됐지만 `EX`·`VE` 대분류 제한으로 제외됐다.
- 군산 `책방` 검색 결과는 `AC` 대분류 때문에 제외됐다.
- 이 결과를 근거로 복수 검색어와 제한된 교차 대분류 허용을 R16.1에 반영했다.
- 변경 후 같은 14개 표본은 12개 조합이 비어 있지 않았다. 통영 음악·공예, 군산 책방, 전주 전통주, 안동 전통주가 복구됐고 강릉·전주 책방은 계속 0건이다.
- 첫 변경 표본에서 전주가 전북 전체를 조회해 남원 장소까지 섞이는 기존 오류를 발견했다. 전주 완산구·덕진구와 포항 남구·북구를 각각 조회해 합치도록 지역 경계를 보정했으며, 보정 뒤 전주 공예는 전주 소속 6건만 남았다.
- 전수 감사 CLI는 현재 만들지 않는다. 필요할 때 승인된 제한 smoke로 재검증한다.

### 결정 필요

- 감사 대상 지역 범위 (전체 vs 주요 지역 샘플)
- 실행 방식 (수동 실행 vs CI)
