# R17 AI 여행 도우미 최종 의사결정 기록

> 담당: 황찬우
>
> 확정일: 2026-08-27
>
> 목표 시점: 2026-08-29 토요일까지 핵심 흐름 대부분 구현
>
> 상태: **PR #24 main 병합·Backend/Flutter CI와 독립 리뷰 완료 — OpenRouter live smoke 대기**
>
> 적용 범위: AI 여행 대화, 장소 추천, 코스 초안, 기존 코스 다듬기,
> MySQL·TourAPI 후보 수집, OpenRouter 사용 경계, 세션 문맥

이 문서는 R17 구현 직전에 황찬우와 확정한 제품·데이터·LLM·세션 의사결정을 한곳에
정리한 기준 문서다. 새 작업 세션은 이 문서를 가장 먼저 읽는다. 다른 현행 AI 문서와
내용이 충돌하면 이 문서를 우선한다. 현재 `main`에는 이 계약의 Backend와 Flutter
구현이 반영됐으며, 남은 R17 완료 조건은 제한된 OpenRouter·MySQL·TourAPI 실환경
smoke다.

## 1. 현재 상황과 결정 배경

R16.3까지 `main`에 병합된 뒤 과거 Qdrant 기반 R17 초안을 MySQL·TourAPI 설계로
전환했고, PR #24로 `main`에 병합했다. 재사용 가능한 Flutter 대화 UI·오류 처리·장소
카드는 유지하고 Backend의 후보 결정 경로와 코스 변환 안전 경계는 새 계약으로
교체했다.

구조를 바꾸는 이유는 다음과 같다.

1. 공모전 일정상 2026-08-29까지 핵심 사용 흐름을 검증해야 한다.
2. 지역과 10개 문화 카테고리는 구조화된 조건이라 제출 전에는 벡터 DB 없이도
   결정론적으로 후보를 좁힐 수 있다.
3. Qdrant·embedding·인덱싱·live 검색 평가까지 유지하면 장애 지점과 비용, 구현 범위가
   증가한다.
4. LLM이 관광지를 직접 고르면 허위 장소·잘못된 `contentId`·검증되지 않은 사실이
   사용자 코스에 들어갈 위험이 있다.
5. 반대로 자연어 문맥과 후속 지시는 단순 키워드 규칙만으로 안정적으로 처리하기 어렵다.

따라서 **자연어 이해는 LLM을 제한적으로 사용하고, 실제 데이터 검색·후보 결정·저장
검증은 Backend의 결정론적 로직이 담당하는 하이브리드 구조**로 확정한다.

## 2. 최종 사용자 경험

### 2.1 하나의 AI 여행 도우미 화면

일반 여행 질문과 코스 다듬기는 서로 다른 챗봇을 만들지 않는다. Flutter에서는 하나의
AI 여행 도우미 화면과 하나의 대화 경험을 제공하고, 진입점이 전달하는 문맥만 다르게
한다.

| 진입점 | 초기 문맥 | 첫 화면의 목적 |
| --- | --- | --- |
| 하단 AI 탭 또는 만들기의 AI 진입 | 일반 탐색 문맥 | 지역·문화·동행·취향 상담과 장소 발견 |
| 코스 상세의 `AI로 다듬기` | `courseId`가 있는 코스 문맥 | 현재 코스 설명, 제한된 편집, 추가 장소 상담 |

코스에서 진입해도 사용자는 새로운 장소나 다른 문화 카테고리를 질문할 수 있다. 일반
탭에서 시작해도 대화 중 검증된 장소로 코스 초안을 만들 수 있다. 차이는 기능 자체가
아니라 시작할 때 Backend에 현재 코스 문맥이 있느냐이다.

### 2.2 대표 다중 대화 유스케이스

```text
사용자: 바다 보고 싶은데 어딜 가는 게 좋을까?
도우미: 지원 지역 중 바다 여행 후보와 추가 확인 질문 제시

사용자: 동행인 대부분이 중년층인데 어떤 주제가 좋을까?
도우미: 이전의 바다 선호를 유지하고, 검증 가능한 문화 주제와 장소 특성으로 설명

사용자: 통영으로 코스 만들어줘.
도우미: 지금까지 확정된 통영·문화·동행 조건과 검증 장소로 코스 초안 미리보기 생성

사용자: 통영의 다른 카테고리도 추천해줘.
도우미: 통영 문맥은 유지하고 새로운 문화 카테고리의 검증 장소 카드 제시

사용자: 그중 가장 평 높은 곳을 추가해줘.
도우미: 신뢰 가능한 평점 데이터가 없음을 알리고, 검증 장소 카드에서 직접 고르도록 안내
```

마지막 예시처럼 데이터가 없는 조건을 LLM의 상식으로 채우지 않는다. CulturePath에는
현재 공통 별점 계약이 없으므로 `가장 평 높은 곳`을 임의로 판단할 수 없다. 현재 R17
챗봇 후보 resolver에는 `publicCourseCount`를 아직 연결하지 않았으므로 이를 평점의
대체값처럼 말하지 않는다. 장소 사용 횟수 UI·정렬 정책이 별도 승인되기 전에는 검증
장소 카드를 보여 주고 사용자가 직접 고르게 한다.

### 2.3 코스 생성과 저장

- 대화 중 `코스 만들어줘`는 즉시 DB 저장을 뜻하지 않는다.
- Backend가 검증한 장소만 사용해 코스 **초안 미리보기**를 만든다.
- 사용자가 Day와 장소 순서를 보고 명시적으로 확인해야 기존 코스 저장 API로 저장한다.
- 저장 전 취소하면 DB는 바뀌지 않는다.
- 공개 코스를 기반으로 편집할 때는 소유권을 얻기 위한 Fork 계약을 먼저 적용한다.
- 다른 사용자의 공개 코스는 명시적 확인 후 Fork API로 내 코스를 만든 뒤 그 코스 ID로
  AI 화면에 진입한다. Backend transform은 소유 코스가 아니면 `403`으로 차단한다.
- 저장 요청은 서버가 반환한 `revision`을 `expectedRevision`으로 보내며, 더 최신 변경이
  있으면 `409`로 중단하고 최신 코스를 다시 열도록 안내한다.
- 저장 완료는 대화 종료 명령이 아니다. 저장한 코스를 현재 문맥으로 갱신하고 후속 질문을
  계속 받을 수 있다.

## 3. LLM과 Backend의 책임 경계

### 3.1 LLM이 하는 일

LLM의 역할은 세 가지로 제한한다.

1. 여러 턴의 자연어에서 지역·문화·선호·동행·행동 의도를 구조화된 값으로 해석한다.
2. Backend가 검증한 관광지 후보를 근거로 사용자 친화적인 설명을 만든다.
3. 기존 코스를 대상으로 한 편집 요청을 허용된 구조화 연산으로 변환한다.

### 3.2 LLM이 하지 않는 일

- 관광지 DB 또는 검색 엔진 역할
- 검증 후보 밖 신규 장소 생성
- 임의 `contentId`, 주소, 좌표, 운영시간, 평점 또는 가격 생성
- TourAPI 결과의 문화 분류를 임의로 확정
- 실제 좌표·이동시간이 없는 동선 최적화
- 검증되지 않은 접근성·혼잡도·날씨·식이 조건 판단
- 사용자 승인 없는 코스 저장
- Backend가 정한 장소 순위의 임의 교체

### 3.3 Backend가 반드시 하는 일

- JWT 인증과 코스 소유권 확인
- LLM 의도 결과의 allowlist·형식·현재 세션 문맥 검증
- MySQL 캐시 조회와 제한된 TourAPI fallback
- 지역 경계, 문화 분류, 중복 제거, 숫자형 `contentId` 검증
- 클릭·담기 가능한 장소 카드의 원본 데이터 구성
- 코스 초안과 편집안의 Day·순서·중복·개수 검증
- 사용자 승인 전 원본 보존
- 실패·모호함·지원하지 않는 요청을 성공으로 위장하지 않는 처리

## 4. 자연어 의도 해석 방식

### 4.1 순수 Rule-based를 사용하지 않는 이유

정확한 지역명이나 문화명 한 번만 찾는 것은 별칭 사전으로 처리할 수 있다. 그러나 다음
상황은 규칙만으로 처리하기 어렵다.

- `거기`, `그중`, `아까 추천한 카테고리` 같은 대명사
- 앞선 여러 질문에서 누적된 지역·동행·취향
- `코스 만들어줘`, `하나 더 넣어줘`, `첫날로 옮겨줘`처럼 대상에 따라 의미가 달라지는
  지시
- `바다를 보고 싶다`, `조용한 곳`, `부모님과 간다`처럼 공식 문화 코드와 바로 일치하지
  않는 선호
- 지역·문화·코스 편집을 한 문장에 함께 담은 요청

따라서 **LLM 구조화 해석 + Backend 규칙 검증**을 사용한다. Rule-based는 LLM을 없애기
위한 대체물이 아니라 안전장치와 빠른 경로다.

### 4.2 의도 해석 결과

LLM은 자유 형식 결론 대신 strict JSON Schema에 맞는 `ParsedIntent`만 반환한다. 목표
필드는 다음과 같다.

```json
{
  "action": "discover_places",
  "regions": ["tongyeong"],
  "cultures": ["문학"],
  "preferenceTags": ["sea", "quiet"],
  "companions": ["family"],
  "dayCount": null,
  "referencedSourceIds": [],
  "referencedCoursePlaceIds": [],
  "needsClarification": false,
  "clarificationQuestion": null
}
```

`action`은 제출 전 다음 범위로 제한한다.

| action | 의미 | 외부 후보 조회 |
| --- | --- | --- |
| `clarify` | 지역·문화·대상이 모호해 추가 질문 필요 | 하지 않음 |
| `discover_regions` | 선호에 맞는 지원 지역 탐색 | 내부 지역 프로필만 사용 |
| `discover_cultures` | 지역·동행·선호에 맞는 문화 주제 탐색 | 내부 문화·지역 프로필 사용 |
| `discover_places` | 확정된 지역·문화로 장소 후보 조회 | MySQL 우선, 필요 시 TourAPI |
| `create_course_draft` | 검증 후보로 코스 초안 미리보기 | 필요한 후보만 resolver 사용 |
| `edit_course` | 현재 코스의 기존 장소 편집안 생성 | 신규 후보 조회 금지 |
| `explain_place` | 선택한 검증 장소 설명 | 캐시·상세 원본 사용 |
| `unsupported` | 현재 데이터나 기능으로 처리 불가 | 지원 경계 안내 |

### 4.3 Backend 검증

LLM이 반환한 지역·문화·장소 참조는 그대로 신뢰하지 않는다.

1. 지역은 CulturePath 지원 지역 slug와 별칭 목록에 있는지 검사한다.
2. 문화는 고정 10종 목록에 있는지 검사한다.
3. `referencedSourceIds`는 현재 세션의 최근 검증 후보 집합에 있는지 검사한다.
4. `referencedCoursePlaceIds`는 DB에서 다시 조회한 현재 코스 장소에 있는지 검사한다.
5. 앞선 문맥과 충돌하거나 대상이 여러 개면 임의 선택하지 않고 재질문한다.
6. 모델 Schema가 틀리면 한 번의 자동 보정 반복을 만들지 않고 안전한 오류 또는
   재질문으로 종료한다.

정확한 지역·문화명이 포함된 단순 요청은 별칭 사전으로 먼저 찾을 수 있다. 다만 그
결과도 동일한 검증 과정을 거치며, 복잡한 후속 지시는 구조화 의도 해석을 사용한다.

## 5. 세션과 문맥 유지

### 5.1 세션에 유지할 구조화 상태

대화 원문 전체를 매번 사실의 원본으로 사용하지 않는다. Backend는 다음과 같은 최소
구조화 문맥을 유지한다.

- `sessionId`, `userId`, 진입 종류
- 현재 확정 지역과 아직 확정되지 않은 지역 후보
- 현재 문화와 사용자가 추가로 요청한 문화
- 선호 태그, 동행 형태, 여행 일수 등 사용자가 직접 말한 조건
- 최근 검증된 장소 `contentId` 목록과 화면에 제시한 순서
- 현재 `courseId`와 DB에서 다시 읽은 코스 버전 식별 정보
- 아직 적용하지 않은 코스 초안 또는 편집 미리보기 식별 정보
- 마지막으로 처리한 action과 필요한 재질문

장소명·주소·이미지·좌표 같은 사실 필드는 세션 복사본을 최종 원본으로 쓰지 않고 필요할
때 MySQL에서 다시 읽는다.

### 5.2 메시지 한도

- 화면은 현재 대화의 메시지를 계속 보여 줄 수 있다.
- Backend와 OpenRouter에는 최근 연속 메시지 최대 20개만 전달한다.
- 메시지당 최대 2,000자, 전체 최대 8,000자로 제한한다.
- 오래된 메시지는 구조화 세션 요약에 반영한 뒤 모델 입력에서 제외한다.
- 실패 재시도용 UI 메시지나 로딩 placeholder는 모델에 보내지 않는다.
- 질문 원문과 전체 대화는 일반 성공 로그에 기록하지 않는다.

### 5.3 저장 후와 종료 시점

- 사용자가 코스를 확인하고 저장해도 세션을 즉시 삭제하지 않는다.
- 저장된 코스를 다시 조회해 `courseId`와 코스 문맥을 최신 상태로 바꾼다.
- 적용이 끝난 `pendingDraft`·`pendingTransform`만 제거한다.
- 사용자는 같은 세션에서 `다른 카테고리도 추천해줘`, `한 곳 더 보여줘`, `2일차를
  바꿔줘` 같은 후속 요청을 계속할 수 있다.
- 명시적인 `새 대화`, 로그아웃, 사용자 변경 또는 비활성 TTL 만료 때 세션을 종료한다.
- 제출 전 기본 비활성 TTL은 30분으로 두고 환경설정으로 조정 가능하게 한다.
- 제출 전에는 대화 원문을 MySQL에 영구 저장하지 않는다. 단일 Backend 인스턴스의
  짧은 수명 세션 저장소를 사용하며, 프로세스 재시작 시 세션이 사라지는 것을 허용한다.
- 다중 인스턴스 배포나 대화 복원이 필요해지면 Redis와 별도 개인정보·보관 정책을 먼저
  확정한 뒤 확장한다.

## 6. 지역 특성 태그

### 6.1 무엇이며 어디서 오는가

지역 특성 태그는 TourAPI가 완성된 형태로 제공하는 공식 필드도 아니고, LLM이 요청마다
새로 만들어 저장하는 값도 아니다. CulturePath가 지원 지역을 자연어 선호와 연결하기
위해 직접 관리하는 **내부 큐레이션 데이터**다.

예를 들어 사용자가 `바다를 보고 싶다`고 했을 때 공식 문화 10종만으로는 지역 후보를
고르기 어렵다. 이때 검증된 지역 프로필의 `sea` 같은 태그가 지원 지역을 좁히는 힌트가
된다. 태그 자체가 관광지의 운영시간이나 접근성 같은 사실을 증명하지는 않는다.

### 6.2 누가 만드는가

- 초기 목록과 매핑의 구현 책임자는 AI·API 연동 담당인 **황찬우**다.
- 팀원이 관리하는 지역·관광지 데이터 계약과 충돌하지 않도록 임수민과 공유한다.
- 제출 전에는 작은 정적 설정 파일과 자동 테스트로 관리한다.
- 제출 후 운영자가 수정해야 할 규모가 되면 DB 테이블이나 관리자 도구로 옮긴다.
- LLM이 제안한 태그는 검토 없이 코드나 DB에 자동 저장하지 않는다.

### 6.3 생성 원칙

1. 지원 지역과 문화 10종에 필요한 최소 태그만 만든다.
2. 공공기관·TourAPI 원본·팀이 검토한 장소 구성처럼 출처를 확인할 수 있는 근거를 쓴다.
3. `중년층에게 적합`처럼 사람 집단을 단정하는 태그보다 `실내 관람`, `역사·문학 중심`,
   `걷기 구간을 줄일 수 있음`처럼 검증 가능한 장소 특성을 우선한다.
4. 접근성, 무장애 시설, 이동 난이도는 실제 데이터가 없으면 태그로 단정하지 않는다.
5. 현재 구현에서 태그는 지역·문화 후보를 좁히는 힌트로만 사용하며, 장소 순위나 장소
   카드의 사실 필드로 직접 사용하지 않는다.
6. LLM에는 현재 질문과 관련된 검증 태그만 전달할 수 있지만, LLM이 태그를 수정하거나
   새 태그를 확정할 수는 없다.

### 6.4 제출 전 저장 형태

제출 전에는 별도 migration을 추가하지 않고 Backend 설정 모듈에 다음 구조로 관리하는
방식을 채택한다.

```js
{
  region: 'tongyeong',
  tags: ['sea', 'literature', 'music', 'local_food'],
  evidence: ['지원 지역의 검토된 문화 장소 구성'],
}
```

`evidence`는 사용자에게 그대로 표시하는 인용문이 아니라 팀이 태그를 검토하고 회귀
테스트할 수 있는 근거 설명이다. 실제 구현에서 태그명과 파일명은 기존 지역 config와
중복되지 않도록 정한다.

## 7. 관광지 후보 resolver

### 7.1 기본 흐름

```text
검증된 의도와 세션 문맥
→ 지역·문화 hard filter 확정
→ place_query_cache와 places_cache 조회
→ 최신 후보가 충분하면 즉시 재사용
→ 부족하거나 stale이면 제한된 TourAPI 조회
→ normalizeTourPlace
→ 지역 경계 검사
→ classifyTourPlace
→ contentId 중복 제거
→ Backend 순위 확정
→ LLM에는 확정 후보만 전달
```

한 번의 장소 조회는 문화 최대 2개로 제한하고, 캐시 서비스를 통과하는 하위 후보 조회도
요청당 최대 12회로 제한한다. 두 문화를 함께 조회하면 예산을 문화별로 균등 배분하고,
보완 검색 중 예산이 소진돼도 이미 확보한 공식 코드 후보는 partial 결과로 보존한다.
여러 시군구를 가진 지역도 문화별로 순차 처리해 동시에 실행되는 하위 요청이 폭증하지
않게 한다. 더 많은 문화는 사용자가 먼저 두 개를 고른 뒤 후속 질문으로 탐색한다.

### 7.2 문화 검색

- 공식 `lclsSystm1~3` 코드로 정확히 구분 가능한 문화는 공식 코드 조회를 우선한다.
- 독립서점·책방처럼 코드만으로 좁히기 어려운 문화는 검토된 복수 검색어로 후보를 넓힌다.
- 검색어 일치는 후보 발견 신호일 뿐 최종 문화 판정 근거가 아니다.
- 최종 문화 판정은 `contentId` override, 공식 세부 분류, 보수적인 제목 규칙 순으로
  검증한다.
- 후보가 적더라도 관련 없는 장소로 개수를 채우지 않는다.

### 7.3 순위

순위는 Backend가 다음의 검증 가능한 신호로 정한다.

1. 요청 지역과 문화의 hard filter 통과
2. 공식 세부 분류 또는 명시적 override 같은 문화 근거 강도
3. 동일 조건에서의 결정론적 tie-break

공개 코스 사용 횟수는 Backend 응답 계약만 존재하며 R17 후보 순위에는 연결하지 않았다.
별도 UI·정렬 결정 전에는 추천 근거나 평점 대체값으로 노출하지 않는다.
지역 특성 태그도 현재는 지역·문화 상담용이며 장소별 태그가 아니므로 장소 순위에 쓰지
않는다.

TourAPI가 공통 별점을 제공한다고 가정하지 않는다. LLM이 인터넷상의 평점이나 인기도를
추측해 순위를 바꾸지 않는다.

## 8. 추천과 코스 편집의 결합 규칙

같은 대화 화면에서 탐색과 편집을 모두 지원하더라도 내부 연산은 섞지 않는다.

### 8.1 추천

- MySQL→TourAPI resolver가 신규 후보를 찾을 수 있다.
- Backend가 만든 장소 카드만 클릭하거나 코스에 담을 수 있다.
- 코스 문맥에서 받은 추천도 자동으로 원본 코스에 삽입하지 않는다.
- 사용자가 카드의 `담기` 또는 초안 확인을 명시적으로 선택해야 한다.

### 8.2 기존 코스 다듬기

- `/ai/transform`은 DB에서 다시 읽은 현재 코스의 장소만 대상으로 한다.
- 허용 연산은 삭제, Day 이동, 대상이 명확한 순서 변경, 유지다.
- 첫 의도 해석은 연산·대상 `contentId`·목적 Day 또는 첫/마지막 위치를 구조화 계획으로
  확정한다. 명시적 장소명·순번은 Backend가 가장 구체적인 단일 대상으로 확인하며,
  모호한 요청은 임의 실행하지 않고 재질문한다.
- 제출 전에는 한 메시지에 한 종류의 편집 연산만 허용한다. 삭제와 Day 이동처럼 서로
  다른 연산을 섞으면 한 가지씩 요청하도록 안내한다.
- 두 번째 생성 결과는 Backend가 구조화 계획과 diff를 비교해, 다른 장소 삭제·추가 이동·
  요청하지 않은 재정렬을 차단한다. 성공 설명도 LLM 문구가 아닌 검증 diff에서 만든다.
- 신규 후보 검색, 신규 `contentId` 추가, 장소 교체는 transform 연산에 넣지 않는다.
- `알아서 최적 동선`은 좌표·이동시간 엔진이 없으므로 지원하지 않는다.
- 결과는 미리보기이며 사용자가 적용하기 전 DB를 바꾸지 않는다.

### 8.3 추천 장소를 코스에 넣는 방법

1. 대화가 추천 intent로 전환된다.
2. resolver가 검증 후보와 장소 카드를 반환한다.
3. 사용자가 원하는 카드를 선택한다.
4. 기존 장소 담기 또는 코스 초안 흐름이 `contentId`를 다시 검증한다.
5. 변경 전/후를 확인한 뒤 저장한다.

이 구분으로 사용자는 한 화면에서 자연스럽게 대화하지만, Backend는 `추천 후보 결정`과
`기존 코스 편집 명령`을 서로 다른 안전 경계로 처리한다.

## 9. API 오케스트레이션 방향

제출 전에는 공개 API를 과도하게 늘리지 않는다.

- `POST /ai/chat`: 세션·의도 해석·추천·설명·재질문·코스 초안 대화를 담당한다.
- `POST /ai/transform`: 현재 코스 장소만 사용하는 strict 편집 미리보기를 담당한다.
- 코스 저장: 기존 코스 CRUD·빌더 저장 경로를 재사용한다.
- 장소 상세·담기: 기존 숫자형 `contentId` 기반 경로를 재사용한다.

`POST /ai/chat`은 목표적으로 다음 문맥을 받을 수 있다.

```json
{
  "sessionId": "optional-existing-session-id",
  "entryContext": {
    "type": "general_or_course",
    "courseId": 42
  },
  "messages": [
    { "role": "user", "content": "통영의 다른 문화도 추천해줘" }
  ]
}
```

응답은 자연어 `content`, Backend가 만든 `sources`, `sessionId`, 현재 처리한 `action`,
필요한 경우 코스 초안 또는 편집 미리보기 참조를 포함한다. 정확한 JSON 필드와 상태
코드는 구현 시 OpenAPI와 테스트를 함께 고정한다. LLM의 내부 출력 Schema를 그대로
Flutter에 노출하지 않는다.

## 10. 오류와 모호함 처리

| 상황 | 처리 |
| --- | --- |
| 지역이 없음 | 앞선 세션 지역을 사용하고, 없으면 지원 지역을 재질문 |
| 지역 후보가 여러 개 | 임의 선택하지 않고 짧은 선택 질문 |
| 문화가 없음 | 지역·선호 태그로 문화 후보를 설명하고 사용자 확인 |
| `그중`, `거기`의 대상이 불명확 | 최근 후보 집합으로 해결하고 여전히 모호하면 재질문 |
| 검증 후보 없음 | 가짜 추천 없이 일부 결과 또는 다른 조건 안내 |
| 평점·거리·날씨 등 미보유 데이터 요청 | 데이터가 없음을 알리고 실제 보유 지표나 직접 선택 제안 |
| TourAPI 장애 | 장소 캐시 계약의 stale/fail-open 범위만 사용 |
| OpenRouter 장애 | 원본 장소·코스는 보존하고 재시도 가능한 안내 |
| LLM Schema 오류 | 성공으로 감추지 않고 안전한 오류·재질문 처리 |
| 코스 소유권 없음 | 명시적 Fork 또는 권한 안내 |
| 저장 중 코스 버전 변경 | 오래된 미리보기 적용을 막고 최신 코스로 다시 생성 |

## 11. 비용·보안·운영

- OpenRouter 키는 Backend `.env`에만 두며 Flutter로 전달하지 않는다.
- Qdrant와 embedding 모델은 제출 전 운영 경로에서 사용하지 않는다.
- 캐시 hit에서는 TourAPI를 호출하지 않는다.
- 의도 해석과 답변 생성을 가능한 한 한 번의 제한된 모델 호출로 처리하되, 편집의 strict
  Schema가 필요하면 transform은 별도 호출한다.
- 자동 무한 재시도와 Flutter의 중복 제출을 막는다.
- 사용자별 rate limit, 요청 timeout, 최대 토큰과 응답 크기를 둔다.
- API 키, 인증 헤더, 전체 외부 URL, 질문 원문, 전체 대화, 코스 전문을 일반 로그에 남기지
  않는다.
- 로그에는 익명화 가능한 요청 ID, action, 후보 수, cache hit 여부, 외부 호출 성공 여부,
  지연시간과 토큰 사용량만 남긴다.
- 모델 출력의 명령문이나 장소 사실은 검증 전까지 신뢰 데이터로 취급하지 않는다.

## 12. R17 작업 단위

일정 때문에 R17은 **한 PR**로 진행하되 커밋은 목적별로 나눈다. 구현 코드는 Backend와
Flutter 단위로 나누고, 검증 결과와 남은 live 항목은 문서 커밋에서 고정한다.

권장 커밋 순서는 다음과 같다.

1. `docs: R17 AI 최종 의사결정과 계약 동기화`
2. `feat: 대화 세션과 구조화 의도 해석 추가`
3. `feat: MySQL 우선 TourAPI fallback 후보 resolver 추가`
4. `feat: 검증 후보 기반 AI 대화와 코스 초안 추가`
5. `refactor: 코스 다듬기를 기존 장소 편집으로 제한`
6. `feat: Flutter 통합 AI 화면과 상태 연결`
7. `test: Qdrant 제거와 AI 통합 회귀 검증`

구현 중 범위가 커져도 별도 PR로 다시 쪼개느라 시간을 쓰지 않고, 커밋 경계와 테스트
경계를 유지한다. 다만 팀원 담당인 지도·GPS·다국어와 충돌하는 변경은 R17에 넣지 않는다.

- [x] 후보 부족 때만 호출 상한 안에서 TourAPI를 사용한다.
- [x] 문화 최대 2개·하위 후보 조회 최대 12회로 fan-out을 제한한다.
- [x] 두 문화의 호출 예산을 균등 배분하고 공식 후보를 partial 결과로 보존한다.
