# [황찬우 전용] R14 Manus 모바일 프로토타입 실행 프롬프트

> **문서 소유자:** 황찬우
>
> **상태:** Manus 실행 프롬프트 v1 — 프로토타입 생성 및 검수 대기
>
> **기준일:** 2026-08-19
>
> **기준 문서:** [R14 P0 디자인 명세](./R14_FIGMA_P0_DESIGN_SPEC.md) · [R14 디자인 검수표](./R14_DESIGN_REVIEW_CHECKLIST.md)
>
> **후속 작업:** 승인된 Manus 결과만 [Figma 최종 정리 프롬프트](./R14_FIGMA_MAKE_PROMPTS.md)에 반영한다.

## 1. 이 문서의 목적

Manus에서는 반복 생성과 인터랙션 검증을 충분히 수행하고, Figma 무료 AI 크레딧은 최종 토큰·컴포넌트·핸드오프 정리에 집중한다. Manus 결과물은 디자인 프로토타입이며 CulturePath의 Flutter 제품 코드가 아니다.

Manus가 만든 React·Tailwind·웹 코드는 다음 용도로만 사용한다.

- 화면 비율·정보 위계·상호작용을 직접 눌러보는 프로토타입
- 360·390·430px와 긴 글자·오류 상태 검증
- 최종 Figma 원본을 만들기 위한 시각 참고자료

다음 용도로는 사용하지 않는다.

- `frontend/`에 그대로 복사
- Backend·MySQL·Qdrant·OpenRouter·TourAPI 실연결
- GitHub 연결, 커밋, PR 또는 배포
- Manus 임의 이미지를 제품용 관광지 에셋으로 사용

## 2. 시작 전에 Manus에 첨부할 파일

새 Manus 프로젝트 하나를 만들고 다음 두 파일을 첨부한다.

1. `R14_FIGMA_P0_DESIGN_SPEC.md`
2. `R14_DESIGN_REVIEW_CHECKLIST.md`

첨부가 어렵다면 두 문서의 원문을 메시지로 제공해도 된다. 기존 CulturePath 저장소나 `.env`는 업로드하지 않는다. Manus에는 API 키·DB 접속정보·GitHub 토큰이 필요하지 않다.

## 3. 실행 순서

1. **0번 마스터 프롬프트**를 입력하고 Manus가 요약한 계약을 검토한다.
2. 같은 프로젝트에서 1번부터 6번까지 한 번에 하나씩 입력한다.
3. 매 단계에서 직접 모바일 미리보기를 눌러본 뒤 문제가 있으면 7번 교정 프롬프트를 사용한다.
4. 전체 화면이 생기면 8번 자체 검수 프롬프트를 입력한다.
5. Manus의 PASS 판정을 그대로 믿지 않고 황찬우가 디자인 검수표를 두 번 확인한다.
6. 승인된 화면만 Figma에 옮긴다.

Manus가 다음 단계까지 임의로 한꺼번에 진행하려 하면 현재 단계까지만 완성하고 멈추게 한다. 한 단계의 토큰·하단 내비게이션·공통 컴포넌트가 다음 단계에서 바뀌지 않아야 한다.

## 4. 0번 — 프로젝트 계약과 안전 경계

아래 블록 전체를 첫 메시지로 입력한다.

```text
첨부한 `R14_FIGMA_P0_DESIGN_SPEC.md`와 `R14_DESIGN_REVIEW_CHECKLIST.md`를 먼저 끝까지 읽어라. 너는 CulturePath의 시니어 모바일 제품 디자이너이자 인터랙티브 프로토타이퍼다.

목표는 Google Play에 배포할 Flutter Android 앱의 디자인을 검증하기 위한 독립형 모바일 프로토타입을 만드는 것이다. Manus 내부 구현 기술은 React나 Tailwind여도 되지만 결과는 웹사이트나 랜딩페이지가 아니라 Android 앱처럼 보여야 한다. 이 코드는 운영 코드가 아니며 나중에 Flutter에 복사하지 않는다.

작업 우선순위는 다음과 같다.
1. 첨부한 P0 디자인 명세의 제품·데이터·담당 범위 계약
2. 이 대화의 현재 단계 지시
3. 첨부한 검수표의 차단·필수 기준
4. 네가 제안하는 장식이나 기술적 편의

프로토타입 안전 경계:
- CulturePath GitHub 저장소를 연결하거나 수정하지 마라.
- GitHub 로그인, 커밋, PR, 외부 배포를 하지 마라.
- Backend, TourAPI, Google Maps, MySQL, Qdrant, OpenRouter에 접속하지 마라.
- API 키, 토큰, DB 비밀번호, 사용자 로그인을 요구하지 마라.
- 모든 데이터와 상태는 프로젝트 내부의 결정론적 mock fixture로 만든다.
- 네트워크가 없어도 핵심 화면과 상태가 재현되어야 한다.
- 프로토타입 실행 중 Google Fonts CDN을 포함한 외부 폰트·이미지·API 요청을 만들지 마라. Noto 글꼴을 로컬로 사용할 수 없으면 같은 계열의 시스템 fallback을 적용하고 FIGMA_HANDOFF.md에 실제 Figma·Flutter에서는 Noto Serif KR/Noto Sans KR을 사용한다고 기록한다.
- 지도 고도화와 다국어 관광 데이터 기능을 새로 구현하지 마라. 두 기능은 임수민 담당이다.
- 존재하지 않는 날씨, 가격, 거리, 실시간 혼잡도, 별점, 운영정보와 추천 점수를 만들지 마라.
- 실제처럼 보이는 개인정보를 만들지 마라.

프로토타입 규격:
- 기본 모바일 viewport는 390x844px이다.
- 360px와 430px 폭에서도 동작하는 responsive layout을 만든다.
- 넓은 데스크톱 preview에서는 앱을 무작정 늘리지 말고 390px 모바일 canvas를 중앙에 보여준다.
- Android status bar, bottom gesture safe area와 키보드 가림을 고려한다.
- 앱 하단 목적지는 홈, 탐색, 만들기, 내정보 4개이며 동등한 높이와 위계를 가진다.
- 프로토타입 안에서 홈→문화→지역→장소→상세→코스 담기, 탐색→코스 상세, 코스→AI 변경안 흐름을 클릭할 수 있어야 한다.
- `/qa` 또는 앱 내비게이션과 분리된 QA 전용 화면에서 loading, empty, error, stale, image-missing, long-text 상태를 선택해 재현할 수 있게 한다. QA 도구를 실제 앱 하단 탭에는 넣지 마라.

시각 방향은 '한국의 문화 여행 편집지'다. 종이, 잉크, 실제 여행 사진, 지명, 일정 순서와 짧은 편집자 주석이 위계를 만든다. 자동 생성 SaaS 대시보드처럼 보이면 안 된다.

고정 디자인 토큰:
- ink #2B2D42
- paper #F7F3E9
- surface #FFFFFF
- terracotta #C75B39
- mustard #D9A441
- charcoal #1E1E1E
- muted #6F706F
- line #DDD8CE
- success #3F6B50
- danger #A33D32
- 제목은 Noto Serif KR Bold/SemiBold, 본문·버튼·숫자는 Noto Sans KR
- spacing은 4, 8, 12, 16, 20, 24, 32, 40만 우선 사용
- 화면 좌우 여백은 360px에서 16, 390px에서 20, 430px에서 24
- 버튼 radius 10, 입력·작은 표면 8, 사진 카드 12
- 모든 터치 영역 최소 44x44px, 주요 버튼 높이 최소 48px

금지할 시각 패턴:
- 보라색, 네온색, 별, 마법봉과 빛나는 gradient로 AI 표현
- 화면 전체 gradient, glassmorphism, 과한 blur와 그림자
- 모든 정보를 큰 둥근 카드에 넣는 구성
- 일반 문구를 전부 pill로 만드는 구성
- emoji와 임의 일러스트로 정보 또는 사진을 대체
- 장식 때문에 정보·터치 영역·대비가 약해지는 구성

공통 UI를 `CP/AppHeader`, `CP/BottomNav`, `CP/CultureTile`, `CP/CourseRow`, `CP/FeedCourse`, `CP/PlaceMediaCard`, `CP/SegmentedTabs`, `CP/PrimaryButton`, `CP/EmptyState`, `CP/InlineError`, `CP/AiAssist`라는 논리 컴포넌트로 구현한다. 이름은 코드 구조 또는 handoff 문서에서 추적 가능하게 유지한다.

프로젝트 내부에 다음 문서를 유지해라.
- `DESIGN_SYSTEM.md`: 토큰, typography, spacing, radius, motion
- `SCREEN_CONTRACT.md`: 화면 목적, 실제 데이터 필드, nullable 처리, 주요 행동
- `STATE_MATRIX.md`: 화면별 loading, empty, error, stale, image-missing 상태
- `CHANGELOG_DESIGN.md`: 단계마다 변경된 내용과 의도
- `FIGMA_HANDOFF.md`: 최종 Figma로 옮길 컴포넌트, 수치와 열린 문제

아직 화면을 구현하지 마라. 먼저 첨부 문서에서 이해한 서비스 목적, 포함 범위, 제외 범위, 4개 하단 탭, 탐색 3개 탭, 홈 추가 섹션, 실제 사용 가능한 데이터와 금지 데이터를 15개 이하 항목으로 요약해라. 충돌이나 모호함이 있으면 추측하지 말고 표시한 뒤 이 단계에서 멈춰라.
```

Manus의 요약에서 다음이 틀리면 바로 교정한다.

- 탐색 기본 탭은 `내 코스`
- 홈 추가 영역은 `내 코스 이어보기` 하나
- 다국어와 지도 고도화는 제외
- AI는 코스 다듬기 보조
- 실제 서비스·저장소·API에는 연결하지 않음

## 5. 1번 — 기반·모바일 셸·QA 상태 전환기

```text
이제 1단계만 구현해라. 앞서 확정한 계약과 첨부 문서를 바꾸지 마라.

구현 범위:
1. 고정 디자인 토큰과 typography
2. 390x844px Android 모바일 셸
3. 홈, 탐색, 만들기, 내정보의 동등한 CP/BottomNav
4. 공통 논리 컴포넌트의 기본 구조와 상태 스타일
5. 실제 앱 내비게이션과 분리된 `/qa` 상태 전환기
6. DESIGN_SYSTEM.md, STATE_MATRIX.md, CHANGELOG_DESIGN.md 초안

아직 개별 화면을 완성하지 말고, 컴포넌트 gallery와 빈 화면 shell만 만든다. 모든 버튼의 실제 pointer target이 44x44px 이상인지 확인하고, keyboard focus가 보이게 한다. hover는 보조 상태일 뿐 모바일 pressed·focused·disabled가 우선이다.

기본 카드 그림자는 제거하고 얇은 line 또는 paper/surface 면 차이로 구분한다. 만들기 탭을 돌출 FAB로 만들지 않는다. 원형 AI 버튼을 공통 header에 추가하지 않는다.

완료 후 다음만 보고하고 멈춰라.
- 생성한 공통 컴포넌트
- 토큰과 명세에서 벗어난 항목 0개 여부
- 360·390·430px overflow 확인 결과
- 다음 단계에서 해결할 열린 항목
```

## 6. 2번 — 홈·탐색

```text
이제 홈과 탐색만 구현해라. 1단계 토큰, 모바일 셸과 공통 컴포넌트를 재사용하고 새 디자인 시스템을 만들지 마라.

홈 순서:
1. CulturePath 브랜드 제목과 검색 진입
2. 실제 사진 또는 명확한 레이아웃용 placeholder와 짧은 계절 편집 문구
3. '오늘은 어떤 문화를 따라갈까요?'와 2열 문화 10종
4. 로그인 서버 코스 또는 게스트 로컬 코스를 최대 2개 보여주는 '내 코스 이어보기'
5. CP/BottomNav

문화 10종은 독립서점·책방, 문학, 음악, 전통주·양조장, 로컬 미식, 공예·공방, 근대 문화유산, 미술·갤러리, 영화·애니메이션, 커피·카페로 고정한다.

홈에 공개 인기 코스를 넣지 마라. createdAt·updatedAt을 현재 Flutter 모델이 표시하지 않으므로 '방금 편집' 같은 상대 시각을 만들지 마라. 내 코스 없음, 2개 skeleton, 해당 섹션만 오류, image-missing 상태를 `/qa`에서 재현한다.

탐색의 1차 탭은 정확히 '내 코스 / 커뮤니티 / 인기'이며 내 코스가 기본이다.
- 내 코스: 소유 또는 게스트 로컬 코스, 행 전체 상세 진입, overflow 편집·삭제
- 커뮤니티: 공개 코스 피드, '최신 / 인기' segmented control, Switch 금지
- 인기: 1~3위만 mustard로 절제해 구분하고 나머지는 같은 목록

실제 가능한 정보인 작성자, 제목, 설명, Day 수, 장소 수, 좋아요만 사용한다. 메달 emoji와 거대한 랭킹 배지를 쓰지 마라. 세 탭의 loading, empty, error, stale를 `/qa`에서 선택할 수 있게 한다.

홈 문화 타일→문화 화면 placeholder, 탐색 코스→코스 상세 placeholder까지 클릭을 연결한다. placeholder 목적지는 '다음 단계에서 구현'임을 개발용으로만 표시하고 사용자 화면에는 기술 문구를 노출하지 마라.

완료 후 360·390·430px, 긴 코스명, text scale에 해당하는 브라우저 확대 200%를 점검하고 변경 문서를 갱신한 뒤 멈춰라.
```

## 7. 3번 — 문화·지역·관광지

```text
이제 문화 선택→지역 추천→관광지 목록→관광지 상세→연관 장소 흐름만 구현해라. 기존 홈·탐색·토큰을 다시 만들지 마라. 지도 화면이나 목록/지도 전환은 추가하지 마라.

결정론적 mock fixture에서 사용할 수 있는 예시:
- 강릉 오죽헌·시립박물관
- 박경리기념관
- 통영국제음악당
- 통영 중앙시장
- 전주 한옥마을

이름 외에 확인되지 않은 운영시간, 가격, 거리, 평점은 만들지 않는다. nullable 값은 있는 fixture에서만 표시한다.

문화·지역 화면:
- 선택한 문화명과 짧은 정적 설명
- 추천 지역 순서와 읽을 수 있는 근거
- API에 없는 정밀 점수나 실시간 수치 없음

관광지 목록:
- 선택 문화와 지역 맥락 유지
- 사진, 장소명, 제공 가능한 보조 정보, 독립된 '담기'
- 사진·제목의 상세 진입과 담기 터치 영역 분리
- 검증된 결과 최대 20개라는 성격 유지
- 빈 결과를 가짜 장소로 채우지 않음

관광지 상세:
- 0장·1장·여러 장 이미지 갤러리, 최대 10장
- 장소명, 문화, 주소, 운영시간, 휴무, 전화, 주차, 홈페이지, 소개는 값이 있을 때만 표시
- 빈 필드마다 '-' 카드를 만들지 않음
- '이 장소를 코스에 담기'를 주요 행동으로 표시
- 연관 장소 실패는 하단 섹션만 재시도
- TourAPI 출처를 절제해 표기

실제 외부 이미지를 내려받지 말고 로컬 reference placeholder 또는 Manus 내부에서 생성한 레이아웃용 이미지만 사용한다. 모든 이미지는 '제품 사용 전 TourAPI 라이선스 이미지로 교체 필요'라고 FIGMA_HANDOFF.md에 기록한다.

홈 문화 타일에서 이 흐름을 실제로 탐색하고 장소를 mock 코스에 담을 수 있게 한다. loading, empty, error, stale, image-missing, long-title과 연관 장소 부분 오류를 `/qa`에 추가한다. 문서를 갱신하고 점검 결과를 보고한 뒤 멈춰라.
```

## 8. 4번 — 코스 만들기·상세

```text
이제 코스 만들기와 코스 상세만 구현해라. 기존 fixture와 공통 컴포넌트를 재사용한다. 실제 저장이나 로그인 API는 연결하지 말고 세션 내부 mock 상태로만 작동하게 한다.

코스 만들기에는 제목, 설명, Day 1~3, 장소 순번·이름·지역·문화 맥락, 장소 추가, 순서 변경, Day 이동, 제거, 저장이 필요하다. 빈 Day, 검색 중, 저장 중, 저장 실패, 게스트 로컬 저장 상태를 재현한다.

코스 상세에는 제목, 작성자, 설명, Day 수, 장소 수와 Day별 장소 순서를 표시한다. 소유자는 편집할 수 있고 다른 사용자는 원본을 보존한 Fork를 할 수 있어야 한다. 현재 구현에 없는 공유 기능을 새로 만들지 마라.

Day를 큰 둥근 카드 안에 반복 중첩하지 말고 문화 여행 편집지의 일정표처럼 날짜 구분선, 순번과 장소명으로 구성한다. 드래그 핸들만으로 이동 기능을 설명하지 말고 접근 가능한 이동 메뉴나 label을 둔다.

지도는 현재 구현 위치를 나타내는 중립적인 정적 영역으로만 두며 Google Maps를 호출하지 않는다. 새 마커 규칙, 경로선, 목록 연동과 거리 계산을 만들지 않는다.

키보드가 열린 상태에서도 현재 입력과 저장 행동이 가려지지 않게 한다. 관광지 상세의 담기, 탐색의 코스 진입, 코스 만들기·상세를 연결한다. `/qa` 상태와 문서를 갱신하고 360px 긴 장소명과 200% 확대를 확인한 뒤 멈춰라.
```

## 9. 5번 — AI 코스 다듬기

```text
이제 기존 코스를 AI로 다듬는 흐름만 구현해라. 실제 Qdrant, OpenRouter나 Backend는 호출하지 말고 결정론적 성공·실패 fixture를 사용한다. 자유 대화형 챗봇으로 바꾸지 마라.

흐름:
1. 사용자가 코스 상세에서 'AI로 다듬기' 선택
2. 원하는 조건을 한 번에 입력
3. 처리 중에도 원본 보존 안내
4. 요청 요약과 변경안 preview
5. 추가·제거·이동·유지된 장소를 색뿐 아니라 label·icon·설명으로 구분
6. 적용 또는 취소
7. 적용 후 원본 복구

보라색, 별, 마법봉과 빛나는 gradient를 사용하지 마라. AI는 CP/AiAssist와 'AI로 다듬기' 문구에 한정한다. 내부 공급자 이름과 오류 코드를 사용자에게 노출하지 않는다.

fixture 상태:
- 입력 전
- 처리 중
- 변경안 성공
- 변경 없음
- 일부 장소 검증 실패
- 검색 실패
- 생성 실패
- 적용 중
- 적용 완료
- 취소 및 원본 복구 확인

실패 상태는 원본이 안전한지, 재시도할 수 있는지, 다음 행동이 무엇인지 알려야 한다. mock 적용 전후의 코스 상태가 실제로 전환되고 복구되어야 한다. `/qa`와 문서를 갱신하고 text scale 200%에서 긴 변경 설명을 확인한 뒤 멈춰라.
```

DESIGN_SYSTEM.md, SCREEN_CONTRACT.md, STATE_MATRIX.md, CHANGELOG_DESIGN.md를 최종화한다. FIGMA_HANDOFF.md에는 다음을 표로 정리한다.

## 12. 8번 — Manus 자체 2회 검수

```text
첨부한 `R14_DESIGN_REVIEW_CHECKLIST.md`를 다시 처음부터 읽고 전체 프로토타입을 두 번 검수해라. 지금은 디자인을 먼저 수정하지 마라.

1차 검수는 정보구조, 실제 데이터 계약, 담당 범위, 핵심 흐름을 확인한다.
2차 검수는 첫 판정을 전제로 삼지 말고 360px, text zoom 200%, loading·empty·error·stale·image-missing, 터치 영역, 대비와 Flutter 재현 가능성부터 다시 확인한다.

각 항목을 PASS, FAIL, NOT_TESTED로 판정하고 근거가 되는 route·화면·컴포넌트와 재현 절차를 적어라. 실제로 확인하지 않은 항목을 PASS로 표시하지 마라. 심각도는 blocker, required, improvement로 구분한다.

보고 순서:
1. blocker 발견 사항
2. required 발견 사항
3. improvement 발견 사항
4. 1차와 2차 판정이 달라진 항목
5. 자동으로 수정해도 계약을 바꾸지 않는 항목
6. 황찬우 결정이 필요한 항목

보고 후 멈춰라. 내 승인 없이 자동 수정하거나 배포하지 마라.
```

검수 보고서를 받은 다음에는 blocker와 required 중 승인된 수정만 Manus에 지시한다. 수정 후 8번 검수를 다시 실행하며, 최종 승인 판단은 Manus가 아니라 황찬우가 한다.
