# AI 기능 개편 계약 — MySQL·TourAPI 기반 탐색과 기존 장소 코스 편집

> 담당: 황찬우
>
> 승인일: 2026-08-26
>
> 상태: **PR #24 main 병합·Backend/Flutter CI 완료 — OpenRouter live smoke 대기**
> 적용 대상: `POST /ai/chat`, `POST /ai/transform`

> 2026-08-27 이후의 통합 화면, 다중 턴 세션, 코스 초안, 지역 특성 태그 결정은
> [R17 AI 여행 도우미 최종 의사결정 기록](./R17_AI_ASSISTANT_DECISION_RECORD.md)을
> 우선한다.

이 문서는 CulturePath AI 기능의 최신 제품·데이터 계약이다. 기존 Qdrant·BGE-M3 기반
RAG 설계보다 우선한다. 현재 `main`의 활성 AI 요청 경로는 이 계약으로 전환됐으며,
과거 벡터 검색 모듈과 수동 평가 스크립트는 운영 경로에서 호출되지 않는 이력 코드다.

## 1. 한 문장 원칙

**LLM은 다중 턴의 자연어 의도를 strict Schema로 해석할 수 있지만, 관광지를 검색하거나
신규 후보를 결정하지 않는다. 여행 챗봇에서는 Backend가 MySQL과 TourAPI로 검증한
관광정보를 자연어로 설명하고, 코스 다듬기에서는 사용자의 자연어 요청을 기존 장소만
사용하는 제한된 편집 연산으로 변환한다. 모든 의도, 장소와 변경 결과는 Backend가
검증한다.**

LLM의 역할은 다음 세 가지뿐이다.

1. 여러 턴의 지역·문화·선호·행동 의도를 제한된 구조로 해석한다.
2. 검증된 관광정보를 읽기 쉬운 답변으로 표현한다.
3. 기존 코스에 대한 자연어 편집 요청을 제한된 구조화 명령으로 해석한다.

LLM은 관광지 DB, 검색 엔진, 신규 후보 생성기, 좌표·거리 계산기 또는 장소 사실의
원본으로 사용하지 않는다.

## 2. 기능별 역할 분리

| 기능 | 목적 | 신규 장소 탐색 | LLM 역할 | 최종 검증 |
| --- | --- | --- | --- | --- |
| AI 여행 챗봇 | 지역·문화에 맞는 장소 발견 | 허용. MySQL 우선, 부족하면 TourAPI | 검증된 후보 설명 | Backend |
| AI 코스 다듬기 | 사용자가 이미 만든 코스 편집 | 금지 | 자연어를 삭제·Day 이동·명시적 순서 변경으로 변환 | Backend |

두 기능은 Backend의 안전 경계로는 분리하되 Flutter에서는 하나의 AI 여행 도우미
대화 화면으로 연결한다. 일반 진입은 탐색 문맥으로, 코스 상세의 `AI로 다듬기` 진입은
현재 `courseId`가 포함된 문맥으로 시작한다.

- 장소가 필요하면 검증된 추천 카드를 받고 사용자가 직접 코스에 담는다.
- 이미 담은 장소를 바꾸면 변경안을 확인한 뒤 적용한다.
- 코스 문맥에서도 추가 장소를 상담할 수 있지만 transform이 신규 장소를 자동으로
  삽입하지는 않는다.

## 3. AI 여행 챗봇 흐름

```text
사용자 질문
→ LLM의 strict 의도 해석과 Backend의 allowlist·세션 검증
→ MySQL의 장소·질의 캐시 조회
→ 후보가 부족하거나 갱신이 필요하면 TourAPI 조회
→ 정규화·지역 경계·문화 분류·중복 제거
→ 검증된 관광지 후보 확정
→ LLM에 후보와 질문 전달
→ 자연어 답변 생성
→ Backend가 후보에서만 장소 카드를 구성
→ 답변 + 신뢰된 장소 카드 반환
```

### 3.1 지역·문화와 행동 의도 해석

- 정확한 지역·문화명은 Backend의 지원 목록과 별칭으로 빠르게 추출할 수 있다.
- 대명사, 누적 선호, 동행, 코스 생성·편집 같은 다중 턴 의도는 LLM이 strict Schema로
  해석한다.
- LLM 결과의 지역·문화·장소 참조는 Backend가 allowlist와 현재 세션 후보로 재검증한다.
- 해석이 불충분하거나 여러 대상으로 갈리면 임의 지역·문화를 확정하지 않고 재질문한다.
- 자세한 Schema와 세션 정책은
  [R17 최종 의사결정 기록](./R17_AI_ASSISTANT_DECISION_RECORD.md)을 따른다.

### 3.2 MySQL 우선과 TourAPI 보완

- `places_cache`와 `place_query_cache`에 조건에 맞는 최신 후보가 충분하면 외부 호출 없이
  재사용한다.
- 후보가 부족하거나 캐시 갱신이 필요할 때만 TourAPI를 호출한다.
- TourAPI 결과는 기존 장소 정규화·캐시·분류 계약을 거쳐 MySQL에 반영한다.
- 캐시의 정확한 TTL, stale, fail-open 정책은
  [장소 캐시 계약](./PLACE_CACHE_CONTRACT.md)을 따른다.
- 후보가 끝내 부족하면 가짜 장소로 채우지 않고 검증된 일부 결과 또는 명확한 빈 결과를
  반환한다.

### 3.3 문화별 후보 수집

문화 검색은 두 전략을 함께 사용한다.

1. TourAPI 공식 `lclsSystm1~3` 코드로 정확히 식별 가능한 문화는 공식 코드 기반 조회와
   분류를 우선한다.
2. 독립서점·책방처럼 공식 코드 하나로 충분히 구분하기 어려운 문화는 검토된 복수
   검색어로 후보를 넓힌 뒤 현재의 엄격한 문화 분류 규칙으로 다시 걸러낸다.

검색어에 걸렸다는 사실만으로 문화 일치로 인정하지 않는다. 최종 후보는 `contentId`
override, 공식 중·소분류 코드, 보수적인 제목 규칙의 우선순위로 검증한다. 세부 규칙은
[TourAPI 장소 계약](./TOUR_PLACE_CONTRACT.md)을 따른다.

### 3.4 LLM 입력과 출력의 신뢰 경계

- LLM에는 Backend가 확정한 후보만 제공한다.
- LLM이 후보 밖의 장소를 언급해도 Backend는 이를 장소 카드로 만들지 않는다.
- 클릭 가능한 `sources`는 Backend가 후보의 숫자형 TourAPI `contentId`로 직접 구성한다.
- 장소명·주소·분류·이미지 등 사실 필드는 LLM 출력이 아니라 MySQL/TourAPI 원본을 쓴다.
- OpenRouter 키와 모델 호출은 Backend에서만 수행한다.

## 4. AI 코스 다듬기 흐름

```text
저장된 현재 코스 조회
→ 사용자 자연어 편집 요청
→ LLM이 제한된 편집 연산으로 변환
→ Backend가 소유권·contentId·Day·순서·중복·한도 검증
→ 변경 전/후 미리보기 반환
→ 사용자 승인
→ 기존 저장 흐름으로 반영
```

### 4.1 제출 전 허용 범위

- 기존 장소 삭제
- 기존 장소의 Day 이동
- 사용자가 대상을 명확히 지정한 순서 변경
- 변경하지 않을 장소 유지

예시는 다음과 같다.

- `경복궁을 첫 번째로 옮겨줘.`
- `2일차 카페를 빼줘.`
- `1일차 장소 두 개를 2일차로 옮겨줘.`
- `박물관은 마지막에 가게 해줘.`

### 4.2 제출 전 금지·보류 범위

- 신규 장소 자동 검색·추가·교체
- TourAPI·Qdrant·embedding 호출
- 후보 밖 `contentId` 생성 또는 사용
- 거리·이동시간 없이 수행하는 `최적 동선` 판단
- 날씨·식이·접근성처럼 원본에 검증 필드가 없는 조건을 사실처럼 판단
- 사용자 승인 전 원본 코스 저장 또는 덮어쓰기

`동선을 알아서 최적화해줘`처럼 실제 좌표 기반 계산이 필요한 요청은 현재 지원하지
않음을 안내한다. 장소를 추가하려는 사용자는 AI 여행 챗봇의 검증된 추천 카드에서 직접
선택한다.

### 4.3 원본 보호

- Backend는 `courseId`로 현재 코스를 다시 조회하고 클라이언트의 장소 객체를 신뢰하지
  않는다.
- LLM이 반환할 수 있는 장소 ID의 허용 목록은 현재 코스의 `contentId` 집합뿐이다.
- 결과의 장소, Day, 순서, 중복과 최대 개수를 Backend가 재검증한다.
- 적용 전에는 DB를 변경하지 않고 변경 전/후 미리보기를 반환한다.
- 타인의 공개 코스는 사용자가 명시적으로 Fork한 자기 코스에만 적용한다.
- 제목·설명 자동 수정은 이번 장소 편집 계약에 포함하지 않으며 기본적으로 원본을
  유지한다. 향후 필요하면 별도 제품 결정을 거친다.

## 5. Qdrant·BGE-M3 처리 방침

- 공모전 제출 전 운영 경로에서 Qdrant와 BGE-M3를 사용하지 않는다.
- `/ai/chat`은 MySQL과 TourAPI의 검증된 후보를 사용한다.
- `/ai/transform`은 현재 코스의 기존 장소만 사용한다.
- Qdrant 컬렉션 생성·재색인·검색 평가와 embedding 호출은 현행 완료 조건에서 제외한다.
- 기존 코드와 테스트는 목표 계약으로 전환하는 PR에서 활성 경로·환경변수·문서·평가
  기준을 함께 정리한다.
- 과거 설계와 실행서는 [`decay`](./decay/README.md)에 보관하며 현행 구현 지침으로 쓰지
  않는다.

이 결정은 벡터 검색 기술 자체를 부정하는 것이 아니다. 현재 제품의 지역·문화 조건이
구조화되어 있고, 제한된 기간과 비용 안에서 검증 가능성을 높이기 위한 제출 전 범위
축소다. 의미 검색이 필요한 자유 질의·개인화 기능이 명확해지면 제출 후 별도 검토한다.

## 6. 비용과 장애 영향

- embedding과 Qdrant 운영 비용·인덱싱 작업이 사라진다.
- 캐시 적중 시 TourAPI 호출 없이 OpenRouter 생성 호출만 사용한다.
- 캐시 미스 시에도 TourAPI 후보 수집과 OpenRouter 답변 생성으로 호출 경로가 단순해진다.
- OpenRouter 장애가 나도 검증된 장소 데이터 자체가 손상되지는 않는다. 사용자에게 재시도
  가능 상태를 제공한다.
- TourAPI 장애 시 장소 캐시 계약의 stale/fail-open 범위 안에서만 기존 후보를 사용한다.
- LLM 장애나 잘못된 구조화 출력은 성공으로 감추지 않으며 원본 코스를 보존한다.

## 8. 제출 후 확장 후보

- 추천 장소를 자동 삽입하는 코스 편집 연산
- 좌표·이동시간 엔진을 붙인 실제 동선 최적화
- 대화 저장과 스트리밍
- 구조화 필터만으로 부족한 사용 사례가 확인됐을 때 의미 검색 재검토

확장 기능도 `검증된 데이터 → 제한된 LLM 역할 → Backend 재검증 → 사용자 승인` 원칙을
유지한다.
