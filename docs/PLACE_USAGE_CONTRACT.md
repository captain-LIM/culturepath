# 공개 코스 장소 사용 횟수 계약

이 문서는 지역·문화별 관광지에 공개 코스 사용 횟수를 결합하는 Backend 계약을 정의한다. 사용 횟수는 문화 관련도를 대체하는 추천 점수가 아니라, 사용자가 실제 공개 코스에 장소를 담은 정도를 설명하는 독립 보조 지표다.

## 집계 기준

- `courses.is_public = TRUE`인 코스만 집계한다.
- 장소 식별자는 `course_tracks.content_id`를 사용한다.
- 같은 코스의 여러 Day 또는 순서에 같은 `contentId`가 반복돼도 한 번만 센다.
- 서로 다른 공개 코스에 담긴 경우 코스별로 한 번씩 센다.
- 코스가 비공개로 전환되거나 삭제되면 다음 조회부터 집계에서 제외된다.
- `content_id`가 `NULL`이거나 빈 값인 트랙은 집계 대상이 아니다.
- 좋아요, Fork, 완주, 조회 수와 합성하지 않는다.

## 조회 방식과 인덱스

장소 한 건마다 쿼리하지 않는다. 지역 장소 한 페이지의 `contentId`를 중복 제거한 뒤 단일 `IN` 집계 쿼리에서 `COUNT(DISTINCT course_id)`를 계산한다. Repository는 한 번에 최대 250개 ID를 허용하고, 현재 지역 장소 API의 페이지당 최대 50개 계약을 충분히 수용한다.

`course_tracks(content_id, course_id)` 복합 인덱스를 사용한다. 신규 DB는 `schema.sql`, 기존 DB는 `20260825_add_course_place_usage_index.sql` migration으로 같은 인덱스를 얻는다. migration은 이름 있는 잠금을 사용하고 재실행 가능해야 한다.

별도 카운터 테이블은 두지 않는다. 현재 규모에서는 조회 시 집계가 단순하고, 코스 수정·공개 전환·삭제와 카운터의 불일치 위험을 피할 수 있다.

집계는 연결 획득과 SQL 실행에 각각 1초의 경계를 둔다. 연결을 제때 얻지 못하면 늦게 도착한 연결을 즉시 반환하고, 실행 중 시간 경계를 넘으면 해당 연결을 폐기한다. 집계 Repository가 동시에 기다리는 연결 획득은 최대 4개로 제한하며 그 이후 요청은 MySQL pool 대기열에 추가하지 않고 즉시 실패한다. 모든 경우 아래의 nullable fail-open 계약으로 처리한다.

## 공개 응답

`GET /regions/:code/spots`의 각 배열 항목에 `publicCourseCount`를 추가한다.

```json
{
  "contentId": "129784",
  "title": "강릉 오죽헌·시립박물관",
  "publicCourseCount": 18
}
```

- 정상 집계 결과가 없으면 `0`이다.
- MySQL 집계가 실패하거나 집계값을 신뢰할 수 없으면 `null`이다.
- 집계 장애는 보조 지표 장애로 취급한다. 장소 목록은 그대로 `200`으로 반환하고 서버에는 비민감 오류 유형만 경고로 남긴다.
- 사용 횟수를 붙여도 기존 문화 관련도 정렬과 TourAPI 발견 순서를 바꾸지 않는다.
- 사용자 ID, 코스 ID, 비공개 코스 존재 여부는 응답에 노출하지 않는다.

## 현재 제외 범위

- Flutter `SpotItem` 파싱 및 장소 카드 표시
- `공개 코스 N개에 담김` 다국어 UI 문구
- 사용 횟수순 또는 관련도 동률 정렬
- 장소 상세·검색·연관 장소 API로의 필드 확장
- 카운터 캐시 또는 사전 집계 테이블

Flutter는 알 수 없는 JSON 필드를 무시하므로 이번 응답 필드 추가는 현재 클라이언트와 하위 호환된다. 화면 표시는 R16.2 추가 로딩 이후 별도 범위로 결정한다.
