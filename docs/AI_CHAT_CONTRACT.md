# AI 여행 챗봇 API 계약

> 담당: 황찬우
>
> 적용 범위: `POST /ai/chat`, 세션 종료·저장 동기화 API
> 상태: **구현 반영 완료 — Flutter CI·OpenRouter live smoke 대기**

> 통합 화면, 다중 턴 세션, 코스 초안과 지역 특성 태그의 최종 결정은
> [R17 AI 여행 도우미 최종 의사결정 기록](./R17_AI_ASSISTANT_DECISION_RECORD.md)을
> 우선한다.

이 문서는 AI 여행 챗봇의 공개 API와 신뢰 경계를 정의한다. 전체 구조와 코스 다듬기와의
역할 분리는 [AI 기능 개편 계약](./AI_MYSQL_TOURAPI_LLM_TARGET_ARCHITECTURE.md)을 따른다.

## 1. 제품 범위

AI 여행 챗봇은 여러 턴의 여행 질문에서 지원 지역·문화·선호·행동 의도를 이어 받고,
Backend가 확인한 관광지만 추천·설명한다.

- 진입점: 하단 AI 탭·Flutter `만들기` 화면·코스 상세의 `AI로 다듬기`
- 화면 경로: `/ai-assistant`
- API: JWT 인증이 필요한 `POST /ai/chat`
- 신규 장소 발견: 허용하되 MySQL→TourAPI 후보 resolver만 사용
- 코스 초안: 검증 후보만 사용한 미리보기와 사용자 확인 후 저장 허용
- 코스 수정: 같은 화면에서 상담하되 실제 편집 미리보기는 `/ai/transform` 계약 사용
- 대화 보관: 짧은 수명 서버 세션에 구조화 문맥만 유지하고 MySQL에는 영구 저장하지 않음
- 입력 한도: 최대 20개 메시지, 메시지당 2,000자, 본문 전체 8,000자

화면에는 전체 대화를 유지하되 서버에는 최신 질문을 포함하는 최근 연속 메시지만 한도
안에서 보낸다. 전송에서 제외된 과거 메시지도 화면에서 지우지 않는다.

## 2. 후보 결정 흐름

```text
질문
→ LLM strict 의도 해석과 Backend allowlist·세션 검증
→ MySQL 캐시 조회
→ 부족하거나 갱신 필요 시 TourAPI 조회
→ 정규화·지역 경계·문화 분류·중복 제거
→ 검증된 후보 확정
→ LLM 설명 생성
→ Backend가 후보에서만 sources 구성
```

- 정확한 지역·문화 별칭은 Backend가 빠르게 찾고, 대명사·누적 선호·복합 행동은 LLM의
  strict Schema로 해석한다.
- LLM의 지역·문화·장소 참조는 Backend가 지원 목록과 현재 세션 후보로 재검증한다.
- 후보 검색과 최종 후보 결정에는 LLM을 사용하지 않는다.
- 정확히 매핑 가능한 문화는 TourAPI 공식 `lclsSystm1~3` 코드를 우선한다.
- 공식 코드만으로 모호한 문화는 검토된 복수 검색어로 후보를 넓힌 뒤 엄격하게 다시
  분류한다.
- 검색어 일치만으로 문화가 맞다고 간주하지 않는다.
- 캐시가 충분하고 최신이면 TourAPI를 호출하지 않는다.
- 후보가 부족하면 가짜 장소나 모델의 지식으로 채우지 않는다.
- 정확한 캐시 상태와 문화 분류는 각각 [장소 캐시 계약](./PLACE_CACHE_CONTRACT.md),
  [TourAPI 장소 계약](./TOUR_PLACE_CONTRACT.md)을 따른다.

## 3. 응답 및 장소 이동 계약

```json
{
  "content": "검증된 후보를 바탕으로 작성한 답변",
  "sources": [
    {
      "contentId": "129784",
      "title": "강릉 오죽헌·시립박물관",
      "address": "강원특별자치도 강릉시 ...",
      "category": "문학",
      "region": "강릉"
    }
  ],
  "suggestedCourse": null
}
```

`content`는 LLM이 검증된 후보를 근거로 작성한 자연어 답변이다. `sources`는 Backend가
후보에서 직접 만드는 클릭 가능한 장소 카드이며 다음 조건을 모두 만족해야 한다.

1. 숫자형 TourAPI `contentId`가 있다.
2. 현재 질문의 검증된 후보 집합에 포함된다.
3. MySQL/TourAPI 원본으로 다시 구성된 장소다.
4. 같은 `contentId`는 한 번만 노출한다.

Flutter는 카드를 누르면 `/places/{contentId}`로 이동한다. 표시 필드 `title`, `address`,
`category`, `region`의 결측 보조값은 기존 공개 장소 계약에 맞춰 처리한다. 모델이 본문에
후보 밖 장소를 언급해도 이를 카드나 저장 가능한 장소로 승격하지 않는다.

전환 중 기존 `suggestedCourse`는 `null`을 유지할 수 있다. 목표 구현에서는 검증 후보로
만든 코스 초안 미리보기만 허용하며, 사용자 확인 전에는 저장하지 않는다. 정확한 응답
필드는 OpenAPI와 Flutter 모델을 함께 변경할 때 확정한다. 개별 추천 장소는 Backend가
만든 카드를 통해 직접 담을 수 있다.

## 4. LLM 역할과 금지 사항

LLM은 다음만 한다.

- 검증된 후보와 사용자 질문을 바탕으로 추천 이유를 자연어로 설명
- 후보가 부족할 때 그 한계를 숨기지 않는 사용자 친화적 문장 생성

LLM은 다음을 하지 않는다.

- 관광지 검색, 검증 없는 지역·문화 확정, 신규 후보 생성
- 임의 `contentId`, 장소명, 주소, 운영시간, 좌표 생성
- 후보의 실제 순위를 Backend와 다르게 재결정
- 사용자 확인 없이 코스를 저장하거나 수정

장소의 사실 데이터와 클릭 가능한 카드는 항상 Backend가 소유한다.

## 5. 실패 처리

| 상황 | 사용자 동작·표시 |
| --- | --- |
| 지역·문화가 모호함 | 필요한 조건을 다시 입력하도록 안내 |
| 검증된 후보 없음 | 가짜 추천 없이 빈 결과와 다른 조건 탐색 안내 |
| TourAPI 장애 | 캐시 계약의 허용 범위에서 stale 후보 사용, 불가하면 재시도 안내 |
| `401` | 로그인 필요 안내 |
| `429` | `Retry-After`가 있으면 대기 초를 포함해 안내 |
| `502/503/504` | 관광정보 또는 AI 서비스 일시 장애 안내 |
| 연결·시간 초과 | 네트워크 확인 안내 |
| 잘못된 모델 응답 | 공통 오류 안내, 임의 장소 카드 생성 금지 |

실패한 질문은 화면에 남기며 `다시 시도`를 제공한다. 재시도 시 같은 사용자 메시지를
중복 추가하지 않고, 요청 중에는 추가 전송을 막는다.

## 6. 운영·비용 계약

- OpenRouter 키는 Backend 환경변수에만 둔다.
- 실제 답변 생성에는 OpenRouter가 필요하지만 Qdrant와 embedding 모델은 필요하지 않다.
- 캐시 적중 시 TourAPI를 호출하지 않고 답변 생성만 수행한다.
- 앱 수준 자동 재요청으로 중복 비용을 만들지 않는다.
- 모델·토큰·지연시간 같은 운영 메타데이터는 사용자에게 노출하지 않는다.
- 질문 원문, 전체 대화, API 키는 일반 성공 로그에 남기지 않는다.

환경에서 수행한다.

- [x] Backend 생성 `sources`만 클릭·담기 가능하도록 검증
- [x] 캐시 hit·부족·stale·TourAPI 실패·후보 없음 회귀 계약 유지
